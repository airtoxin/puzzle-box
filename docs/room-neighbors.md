# 部屋間の接触と個数を組み合わせる

島国にある部屋間の条件を、固定された部屋配置に対する2つの断片として扱います。
意味の確認には、実装を提供する [Cross+A の島国ルール](https://www.cross-plus-a.com/html/cros7shim.htm)を参照しています。
どちらも既存の黒白セルと部屋境界を使い、新しい回答形式を必要としません。

| 断片 | 条件 | 含まないもの |
| --- | --- | --- |
| `NoColorAcrossRooms(rooms, black=True)` | 部屋境界を挟んで辺を共有する2セルを、両方とも対象色にしない | 部屋内の接触禁止、角の接触禁止、個数・連結・非空 |
| `AdjacentRoomCountsDiffer(rooms, black=True)` | 辺を共有する部屋ごとに、部屋全体の対象色の個数を異ならせる | 非隣接部屋との比較、セルの接触禁止、連結・非空 |

各々の `black=False` は白を対象にする変種です。2つの対象色は別々に選べます。
既存の黒総数・行列ヒントは、その場合も黒の個数です。

## 2つの条件の違い

接触禁止は**部屋の境界だけ**に適用します。同じ部屋の黒2マスをつなげることは許すため、
盤面全体で黒を非接触にする `NonTouchingBlack` とは異なります。異なる部屋の黒が角だけで接することも許します。

個数の比較は、黒セルの実際の接触ではなく、固定された部屋の隣接関係を使います。
部屋の境界が全て白でも、辺を共有する部屋の個数は比較します。
比較するのは境界上の個数ではなく**各部屋の総数**です。同じ2部屋が複数の辺で接しても、同じ比較を1回だけ追加します。
角だけで接する部屋・離れた部屋なら、同じ個数でも構いません。

0も通常の個数なので、隣接する2部屋が両方空なら個数条件に違反します。
0と1なら通り、隣接相手のない1部屋だけなら空でも通ります。
「全ての部屋に黒が必要」という条件は暗黙に追加しません。
部屋の大きさが違う場合、黒数が等しくても白数は異なることがあります。色を変えると別の制約になります。

## 島国型の小さな例を生成する

[2×3のレシピ](../examples/shading-shimaguni-recipe.json)は、上下の行を別の部屋にし、既存の `RoomConnectedBlack(nonempty=True)` を加えます。
各部屋に黒の島を1個作り、境界を越える黒の接触を禁止し、隣接部屋の黒数を異ならせる3条件です。

```python
from puzzle_defs import (
    AdjacentRoomCountsDiffer, NoColorAcrossRooms, RoomConnectedBlack, ShadingRecipe,
)

rooms = ((0, 0, 0), (1, 1, 1))
recipe = ShadingRecipe(2, 3, (
    RoomConnectedBlack(rooms, nonempty=True),
    NoColorAcrossRooms(rooms),
    AdjacentRoomCountsDiffer(rooms),
))
```

数字のない島国の条件を組み合わせた例で、部屋ごとに異なる固定数字を置く機能は含みません。
基礎ルールだけでは4解あり、セルヒントを2個残して一意にします。生成されたセルヒントは通常の島国の部屋数字とは異なる追加のヒントです。

```sh
uv run --no-sync python examples/generate_shading.py generate --recipe examples/shading-shimaguni-recipe.json --selection finite --seed 0 --output shimaguni.json --quiet
uv run --no-sync python examples/generate_shading.py show shimaguni.json
uv run --no-sync python examples/generate_shading.py verify shimaguni.json
```

`show` の解答テンプレートの `?` を黒 `#` または白 `.` で埋めて確認します。固定環境の seed 0 では次の解答が通ります。
完全解は `show` には出しませんが、保存JSONには答えが含まれます。

```sh
uv run --no-sync python examples/generate_shading.py check shimaguni.json --answer "##./..#"
```

このレシピを行・列の黒数ヒントだけに変えると、全候補を残しても左右反転した解を区別できず、ヒント不足になります。
また「各部屋の黒数を1個」を追加すると、隣接部屋の黒数を異ならせられないため矛盾します。
成立・ヒント不足・入力やUIの不適合は区別します。

## UIと保存契約

Webでは「異なる部屋の対象色を辺で接触させない」「辺で隣り合う部屋の対象色の個数を変える」を選べます。
上の例では初期の黒総数・白連結を外し、「各部屋内で黒をつなぐ」を加え、部屋配置を `0 0 0` / `1 1 1` にします。
ヒントは「黒・白のセルヒント」だけを残します。
共有する部屋入力は1個で、接触と個数それぞれの色は独立した真偽値です。
黒白と部屋の既存描画器を再利用し、線の入力や専用の操作はありません。

宣言は既存の `rooms/region-map` と `rooms/cell-regions`、真偽値 `black` です。
保存IDは `no-color-across-rooms` と `adjacent-room-counts-differ`、各フィールドは `rooms` と `black` です。
JSONでは両フィールドが必要で、未知のフィールド・ID、真偽値以外の色を拒否します。
古い読込器は未知の新IDを拒否し、ファイルからコードを実行しません。

部屋は非空長方形の整数ラベルで、各部屋が上下左右で連結している必要があります。
ラベルを不変の格子へコピーして正規化し、併用する全ての部屋ルールで同じ分割を共有します。
凹凸・空・不連結・範囲外や真偽値のラベル・盤面との寸法不一致・異なる共有配置を拒否します。
黒白以外の盤面プロファイルに、部屋チャンネルの名前だけを使って追加することはできません。

## 実装と限界

接触条件は部屋をまたぐ隣接ペアの対象色の和を1以下にし、個数条件は各部屋の対象色の和を隣接部屋どうしで不等にします。
新しい補助変数は作りません。回答は既存の黒白セルに射影します。
独立判定は座標の距離と各部屋の総数を使います。テストの参照実装は領域のビット集合を上下左右にずらして接触を調べ、ビット数で個数を比較します。
2×3以下の複数配置・両方の色で、参照結果・独立判定・DSLの全回答を照合し、くぼんだ3×3では全512配置について2つの独立判定を比較します。

部屋は固定で生成・削減しません。説明推論は未対応と報告し、唯一解検証では両断片を適用します。
保存CLIは既存の25セル、Webと有限診断は9セルまでです。Webの計算予算を維持し、通常CLIには壁時計の打切りがありません。
唯一解・ヒント既約性は、最少ヒント数・人間の難易度・より大きい盤面の性能・任意のルールの合成を保証しません。
