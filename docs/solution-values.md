# 解から値を読むときの所属と時点

`Solution` は、求解した時点の値と、その変数を作ったモデルを保持します。
`solution.value(var)` と `solution.grid_values(...)` は同じ `Puzzle` の変数だけを読みます。
別のパズルの変数を渡した場合は `ValueError` になります。

以前は変数番号だけで値を取得していたため、別モデルの「1に固定された変数」を渡しても、
その番号にあるローカル変数の値0を返すことがありました。
変数名や盤面の形が同じでも、別の `Puzzle` の変数を読み出すことはできません。

## 求解後にパズルを変更する場合

既存の `Solution` は古い求解結果のスナップショットとして保持されます。
制約を追加して解き直しても、古い解の値は変わりません。
新しい制約を満たす解かどうかは、改めて `puzzle.solve()` の結果を確認してください。

求解後に追加した変数を古い解から読むことはできません。
モデルが同じでも、その解に値が存在しないため `ValueError` になります。
新たに求解した結果からは、新しい変数も読めます。

## 互換性

通常の `Puzzle.solve()`、`Solution.value()`、`Solution.grid_values()` の呼び出し方は変わりません。
通常求解と一意性指定の両方で、モデル情報を持つ `Solution` を返します。

低水準APIとして直接 `Solution(solver)` を構築している外部コードは、
`Solution(solver, model)` に変更する必要があります。リポジトリ内に直接構築する利用者は
`Puzzle.solve()` 以外にはありませんでした。モデルが分からないまま所属を推測する
互換モードは設けていません。

直接構築する場合は、その solver が実際に解いた model を渡してください。
CP-SAT の応答だけから元のモデルを証明することはできないため、この対応は呼び出し側の責任です。
実行不能などの応答からの構築は拒否します。値はコピーして保持するため、
同じ低水準 solver を後から別の問題に使っても、既存の `Solution` は変わりません。

## 検証と限界

別モデルで同じ変数番号が衝突する場合、別の `VarGrid`、求解後に増えた変数、
制約追加後の再求解、低水準 solver の再利用を回帰テストで確認します。
`_internal` やモデルの proto を直接書き換える操作、非Varの式を `value()` に渡す操作は
保証対象外です。大量の解を保持する場合のメモリ使用量の評価も今回は行っていません。
