# マッチング候補の入力契約

`Puzzle.match_var_map(name, left, right, allowed_pairs)` は、単純二部グラフを作ります。
各候補 `(a, b)` に1つの真偽変数が対応し、その候補を使うかどうかを決定します。

## モデルを作る前に検査すること

- `left` 内、`right` 内に重複したキーがないこと。
- `allowed_pairs` に同じ組が重複していないこと。
- 各候補の左端点が `left`、右端点が `right` に宣言されていること。

違反は `ValueError` で拒否し、モデルや変数一覧に途中までの変更を残しません。
キーは従来どおり Hashable が前提です。不正な非Hashable値は Python の `TypeError` になります。
左右で同じラベルを使うことは可能です。例えば `left=[0]`, `right=[0]`,
`allowed_pairs=[(0, 0)]` は、別々の側の頂点を結ぶ正当な候補です。

入力の並び順は維持し、入力リスト自体は変更しません。
重複を自動的に取り除く仕様にはしていません。候補生成の間違いをその場で検出し、
呼び出し側で意味を確認できるようにするためです。

## 修正前に起きていたこと

同じ候補を2回渡すと、変数マップは最後の変数で上書きされましたが、次数の計算では
その変数が2回数えられていました。1本の候補しかないグラフで「次数1」を要求しても、
`2 × 変数 = 1` となり実行不能でした。最初の変数はモデル内に残り、一意性にも影響し得ました。

未宣言の端点を持つ候補は、宣言された側の一部の条件しか適用されませんでした。
左の頂点集合が空なのに、未宣言の左端点から右の頂点へマッチできる反例を確認しています。

## 孤立した頂点と空のグラフ

候補のない頂点は正当な入力です。その次数は0です。
`*_degree_eq(n)` と `*_degree_le(n)` は、候補の有無にかかわらず
同じ合計式を使います。例えば孤立した頂点の次数 `<= -1` は実行不能です。
以前のように候補が空だから条件を無視することはありません。

左右とも頂点が空なら、空のマッチングが1つあります。
この場合、各頂点への次数条件は対象がないため空の条件集合になります。
`right_selected_iff` が渡された変数マップに存在する右頂点だけを結び付ける既存動作は変更しません。

## 互換性と検証

通常の Tents 定義は、頂点と候補がすでに重複なく宣言されているため呼び出し方を変える必要はありません。
一方、重複や未宣言端点に依存していた外部コードは、候補生成側の修正が必要です。
多重辺を表現するAPIではないため、その用途では辺IDを含む別の表現が必要です。

入力拒否後にモデルが変更されないこと、左右の同名ラベル、孤立頂点の左右・等号・上限条件を確認します。
2×2の二部グラフについては、候補集合16通りとそれぞれの選択を全列挙し、
CP-SATを使わない次数の検証器と照合します。大規模なマッチングの性能評価や、
`MatchVarMap` コンストラクタを直接使う内部データの検証は今回の対象外です。
