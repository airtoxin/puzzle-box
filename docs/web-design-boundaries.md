# Web 設計の境界と改善の優先順

ルール定義は盤面と表示要件を宣言し、サーバーが対応可能な組み合わせを検証して plan を返す。ブラウザは自身が実装する表示能力と plan を照合し、未知の盤面・チャンネルを描画しない。両者は別々に配信され得るため、サーバーの宣言をそのままブラウザの対応保証にはしない。

今回の分離では `apps/web/plan-contract.js` が plan の検証、`app.js` が画面と操作を担当する。ローカル HTTP、Git ビルド、限定エクスポートは `examples/web_assets.py` の同じ静的ファイル一覧を使う。表示能力に変更があるときは、宣言、ブラウザの検証と描画、配信成果物、実際の画面テストを合わせて確認する。 カタログ読み込み中は設定操作を無効にして、後から初期値が入力を上書きしないようにする。取得に失敗したときはカタログとプレビューをそれぞれ再試行でき、プレビューの再試行では編集済み設定を保持する。カタログとプレビューは応答本文を含め15秒で打ち切り、通信が止まった場合も再試行できる。古いプレビュー応答は新しい設定を上書きしない。

## 今後の優先事項

1. **宣言から実画面までの一貫性**: 多数のルールは Python の宣言、plan の追加データ、ブラウザの検証・描画にまたがる。特に共有グリッドや固定マスの意味が違うデータを同一視しないよう、各種チャンネルを使った画面テストを保つ。今回の分離は境界を明確にする第一歩であり、これらの対応関係の完全な一元化ではない。
2. **計算の予算と結果の意味**: 黒白の通常生成と解答検証はソルバーを使い、独立した全列挙は小盤面向けに残す。UNSAT と UNKNOWN、唯一性の証明と未確定を区別し、モデル構築を含む重い処理は時間制限のあるワーカーで行う。 ワーカーの応答は JSON の型、証拠の件数、保存形式、要求・解答・ヒント間の軽量な整合性を検査し、不正な結果は未確定にする。これは盤面が全ルールを満たすことや唯一性・既約性の証明を再計算するものではない。複雑な大盤面が制限時間内に完了する保証はない。
3. **保存・公開経路の互換性**: 保存データの形式とルールの意味は既存利用者との契約である。変更時には旧データの読み取り、ローカルと両方の公開成果物、ブラウザの生成から解答確認までを検証する。ルール追加やサイズ上限の変更は今回の対象に含めない。

参照: [Web アプリ](web-app.md)、[生成と計算予算](finite-shading-generation.md)、[公開方法](deploy-vercel.md)、[ルールの盤面上限](shading-rule-limits.md)。

固定グリッドのサーバー側の plan 項目は `examples/web_catalog.py` の `SHADING_PLAN_GRIDS` で表示チャネルと対応づける。各 `shared_*` は従来どおり値の検証と共有条件を担い、対応するチャネルと値の有無が一致しない場合は plan を拒否する。新しい種類を加える際はルールの宣言、共有条件、plan、ブラウザ側の独立した検証・描画と配信経路を併せて確認する。
