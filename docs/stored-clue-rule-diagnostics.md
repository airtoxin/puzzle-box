# 実際に残ったヒントでルールの必要性を調べる

全候補ヒントがあるときに不要なルールでも、ヒントを削減した問題では必要になることがあります。
`diagnose_shading_rules.py` は保存済みの黒白問題を読み、ヒントを固定したまま各ルールを1個ずつ外します。
別解が生じる場合、その数と具体的な盤面を表示します。入力のルールやヒントは変更しません。

## 試す

```sh
uv run --no-sync python examples/generate_shading.py generate --recipe examples/shading-recipe-sample.json --seed 6 --output puzzle.json
uv run --no-sync python examples/diagnose_shading_rules.py puzzle.json --output rule-report.json
```

`--json` を付けると標準出力もJSONになります。`--output` は常にJSONを保存します。
レポートには元の答えと別解が含まれるため、プレイヤー向けのヒントだけの表示ではありません。
同じ入力を別のプロセスで読んでも、同じ環境では同じJSONになります。求解seedは診断には使いません。

## 具体例: 全ヒントでは不要でも、出題後には必要

Python 3.12.14 / OR-Tools 9.15.6755 の上記生成例は、3×3の「黒3個＋黒マス非隣接」です。
全候補ヒントはセル9個・行3個・列3個の計15個ですが、削減後は次の2個だけが残ります。

- 行0の黒数が1。
- 行1の黒数が2。

答えは `.#./#.#/...` です。元のルールとこの2ヒントでは一意です。

| 外すルール | 元の答えから得る全15ヒントを固定 | 実際に残った2ヒントを固定 | 2ヒントを満たす別解の一例 |
| --- | --- | --- | --- |
| 黒3個 | 1解。ルールを外しても一意。 | 2解。ルールが必要。 | `.#./#.#/.#.` — 黒が4個になる。 |
| 黒マス非隣接 | 1解。ルールを外しても一意。 | 9解。ルールが必要。 | `..#/.##/...` — 黒同士が隣接する。 |

`.` は白、`#` は黒、`/` は行の区切りです。各行は別々の実験で、もう一方のルールは維持します。
この2解・9解は最大512配置の全列挙で数え、自動テストでは実際のDSLソルバーが列挙する解とも照合しています。

さらに小さな反例は、2×2・黒1個・左上／右上／左下が白という3ヒントです。
元の答えは `../.#`。全セルヒントなら黒数ルールは不要ですが、3ヒントだけでは黒数を外すと `../..` も答えになります。

## 比較の意味

入力の保存解を `A`、残っているヒントを `H`、`A` からレシピの候補ヒント形式で得る全ヒントを `F(A)` とします。
各ルールを外したモデルについて、`H` と `F(A)` をそれぞれ固定して解数を数えます。
ルールを外した後の別解からヒントを取り直すことはありません。

| JSONの主な項目 | 意味 |
| --- | --- |
| `original_answer_count` | 入力は元のルールと保存ヒントで1解であることを確認する。 |
| `answers_with_stored_clues` / `necessary_with_stored_clues` | そのルールだけを外し、保存ヒントを固定した解数／別解が生じるか。 |
| `answers_with_full_candidate_clues` / `necessary_with_full_candidate_clues` | 同じルールだけを外し、元の保存解の全候補ヒントを固定した解数／別解が生じるか。 |
| `needed_with_stored_but_not_full_clues` | 全候補ヒントでは不要だが、保存ヒントでは必要である。 |
| `stored_clue_alternative` / `full_clue_alternative` | 元の答えとは異なり、対応する固定ヒントと残りの全ルールを満たす具体例。なければ `null`。 |
| `stored_clues_irreducible` / `removable_clue_indices` | 元のルールの下で、保存ヒントを1個だけ外しても一意か。番号は1始まりで、重複したヒントも別の出現として扱う。 |

ここでの「冗長」は、この問題の一意性を保つのにそのルールが不要という意味です。
人間の解き筋で使わない、説明に含める価値がない、すべての問題で不要、といった意味ではありません。

既存の [組合せ探索](shading-exploration.md) はレシピの全完成解について候補ヒントの識別能力を比較します。
この比較は **入力された1個の保存解だけ**が対象です。`comparison_is_for_stored_answer_only` もJSONに記録します。
元々数ヒントだけでルールが必要な場合は、全候補ヒントでも必要と表示します。
例えば3×3の `.../.#./#.#` を全行列ヒントで指定すると、非隣接を外した解は3個になり、削減前から必要です。

## 入力とエラー

- 入力は既存の `puzzle-box/shading-v1` / `shading-v2` の問題JSONです。レシピ・探索レポートは入力にできません。
- 対象は[黒白の組み込みルール](shading-fragments.md)と[固定部屋のルール](room-fragments.md)、9マス・8ルール出現・32ヒント出現以下です。座標、値、ヒント形式を検証してから全列挙します。
- 元のルールと保存ヒントが0解・複数解なら、理由と解数を示して終了コード2にします。保存解が唯一解と一致しない場合も拒否します。
- ヒントが既約であることは必須ではありません。既約かどうかと、個別に削除できるヒント番号をレポートします。実際に生成器で削減された履歴までは証明しません。
- `seed` / `environment` は任意の参考メタデータとして受け取り、診断結果の根拠には使いません。未知の項目や不正な構造は拒否します。
- ファイルはUTF-8のJSON、65,536バイト以下。重複キー・NaN等を拒否します。入力と出力の同一ファイル・別名も拒否し、診断が失敗した場合は既存出力を書き換えません。

基準の問題が一意でない場合に「ルールを外しても一意性を失わなかった」と表示すると、不要だと誤解するため、
このコマンドでは非一意の入力を診断対象にしません。レシピそのものの成立性・ヒント不足は
[小盤面の診断](shading-diagnostics.md)を利用してください。

## 個別の冗長性から一括削除はできない

「黒1個」のルールが2回ある場合、それぞれを1個だけ外してももう一方が残ります。
両方を一括削除すると、上の2×2の問題は2解になります。ヒントにも同様の相互依存があります。
このレポートは自動削除やルールの最小集合を提案しません。

独立した全列挙検査器の `finite_space` / `full_clues` を再利用し、生成器・ソルバーの意味は変更しません。
ルールの削除は制約を緩めるだけで、盤面・ヒントの役割・可視解の射影を変えない既存4型に限定しています。
他の寸法・ルール型・ループ・ヤジリン、任意DSLへの一般化や、人間向け難易度・同時最適化は未対応です。

[レシピの読込](shading-recipe-files.md)と入力検証の処理を共有しますが、
診断入力はレシピではなく生成済みの問題です。
